# Project-aware Hermes conversations

The optional project responder connects authenticated Slack turns to approved project knowledge, canonical work status and scoped persistent learning. Enablement requires the reviewed combined runtime release plus an exact private project manifest path and SHA-256. The existing text-only responder remains available when that explicit configuration is absent. Deployment evidence establishes which version is active.

`startup.ts` composes `ProjectAssistant`, `createCurrentWorkReader` and `createHermesProjectResponder`. Slack admission carries requester, workspace, surface, channel and thread as trusted host fields. A sender ID written inside a message has no authorization effect. Existing membership checks, explicit mentions, delivery receipts and DM isolation remain in place.

The host offers seven tools: `project_list`, `project_read`, `project_search`, `current_work`, `remember_fact`, `recall_learning` and `propose_skill`. Project cards are loaded before the turn; source reads use exact committed blobs and an explicit file list, with hashes and bounded pagination. Git network/protocol/lazy-fetch behavior is disabled. Current work reads selected canonical action and PR metadata; it never reads conversation histories or infers successful tests from a completed action.

Memory is a separate owner-only SQLite file. Tanner can record contextual facts or skill proposals. Private records remain private across threads and restarts; shared records are isolated by channel and project. Other authorized workspace members can read the shared project context but cannot write Tanner's learning store. Repository text and remembered notes remain data and cannot change tool permissions, model routes, credentials, approvals, spending controls or a closed coding trial.

A useful learning loop is: inspect a cited project source, record an attributed discrepancy or lesson, recall it for the next relevant task, propose the workflow correction, then test and review the resulting code or skill change through the existing coding workflow. `propose_skill` records a proposal; it does not install code or claim a review has occurred. The project skill index now discovers both `.agents/skills` and `.claude/skills` with bounded reads and separate source provenance.

Each conversation turn allows up to three physical model requests and six host tool calls, with fixed 1,024 output tokens per request and the same existing $5 conversation allocation. Every request passes the canonical spend guard. There is no retry, fallback, new budget pool or automatic refill, and unknown charges halt later requests. The third request is answer-only. This generation policy is separate from the unchanged persisted history schema and its bounds; deployment pins the new policy through source and manifest hashes without resetting conversation history.

Verification includes real startup-to-Slack-to-current-work fixtures, canonical spend receipts with fake providers, memory reopen/isolation, path and secret refusal, Git transport denial, forged transcript/tool rejection and cleanup failures. A separately reviewed native SDK smoke is needed before claiming actual worker compatibility; live project-aware acceptance is recorded by the deployment operator.
